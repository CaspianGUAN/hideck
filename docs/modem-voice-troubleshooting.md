# 模组直拨音频排障与修复

适用 HiDeck v2.1.24 的模组直拨实现，已在 DJI/Baiwang、QDC507GLEFM21、
USB `2c7c:0125` 和 OpenWrt x86/64 的原生部署及 Docker 部署上验证通话。

## 网页媒体连接

网页拨号准备会等待 WebRTC `connectionState=connected`，最多15秒。
连接失败或超时会释放麦克风和 PeerConnection 并显示错误；`connecting`
不再显示为已就绪。空闲页面不会自行创建通话媒体，点击双向呼叫后才会
准备麦克风和连接。因此空闲时的“未连接”不等于模组不能拨号。

麦克风需要可信 HTTPS，媒体传输使用配置的 WebRTC UDP mux，默认7580。
使用反向代理时同时检查证书信任和浏览器到媒体端口的连通性。

`浏览器媒体连接状态` 日志记录连接变化。`closed` 也可能由正常挂断触发，
不能独立作为网络断线的证据；同时查看通话结束原因和是否出现恢复超时。

## 浏览器到电话端的延迟

实测一通电话的宿主播放管道持续积压25280—25600字节的8kHz单声道
S16_LE音频，相当于1.58—1.60秒；ALSA声卡自身延迟约76—95毫秒。
这说明只缩小声卡 `--buffer-size` 不能消除管道中的历史音频。

修复后的ALSA适配器每20毫秒送一帧，最多保留两帧待播放数据。
Linux用FIONREAD检查播放管道，超过640字节预算时暂停追加；突发包
挤满等待队列时丢弃最旧帧，优先保留最近的语音。输入暂时缺失时写入
零值PCM，保持播放运行。保留原640样本的声卡缓冲，挂断会停止并等待
播放线程退出。

新增回归覆盖突发输入、数据复制、缺包静音及阻塞消费者的关闭。
实际USB声卡隔离测试输入300帧突发（6秒音频），再暂停输入1秒，
观测播放管道没有秒级积压、声卡保持RUNNING。该测试未拨号，不能
替代真实通话的端到端延迟及间歇无声复测。

## 音频诊断日志

- `浏览器首个音频包`：编码和负载大小。
- `浏览器音频包未转发`：第一次不支持的负载及原因。
- `网页音频转发统计`：浏览器包数、拒绝包数、音量峰值及上下行包数。
- `模组音频转发统计`：PCM/RTP帧数、音量峰值、静音及异常来源计数。
- `声卡播放队列统计`：丢弃的过期帧和补入的静音帧。
- 模组通话消失时的CLCC状态和AT+CEER结果，由已有AT队列读取。

这些日志不保存音频内容。AT+CEER代码需要结合对应固件和实际挂断
操作解释，不能只凭一条结果判断运营商故障。上行帧计数表示交给播放
适配器的帧数；丢弃和静音计数用于评估实际播放队列。

## MP3录音与宿主USB设备

静态musl不能动态加载MP3编码库；使用[动态musl构建方式](../packaging/openwrt/README.md#原生动态-musl-二进制通话录音)
并安装 `lame-lib`。已验证2秒合成PCM经HiDeck实际编码器生成MP3。

`USB device has 0 bidirectional PCM endpoints` 表示宿主未枚举可用的
双向USB声卡。模组内部PCM节点或持久USB UAC位为1，不代表当前
宿主已经出现USB Audio接口。检查宿主 `/proc/asound/cards` 和
`/proc/asound/card*/pcm*`，并核对USB当前组合中是否有audio。
本次通过空闲时使模组既有USB配置重新生效恢复枚举；这属于设备运行
状态处理，并未增加自动重启、刷机或无条件修改USB配置的代码。

镜像可以正常通话。容器内的 HiDeck MP3 编码器已通过合成音频验证。
